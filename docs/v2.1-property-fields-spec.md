# AQAR v2.1 Property Fields Specification

## Status

This specification is approved for implementation planning from the saved baseline `v2.0.0-baseline`. It defines the first addition set only; it does not authorize a calibration change, a production evaluator change, or a new Accuracy artifact until the isolated analysis is complete.

## Goals

The release has three equal goals: improve comparable selection and valuation quality, make property data easier to enter, and explain the result more clearly. Existing fields must remain available and retain their current semantics.

## Existing fields that remain unchanged

`Detailed Unit Type`, `Floor`, and `Parking Count` remain in the first release exactly as they are. No existing property type, valuation method, calibration field, or current behavior is removed or redefined.

## New fields and applicability

| Property type | Project / Building Name | BUA | Plot Area | Last Renovation Year |
|---|---:|---:|---:|---:|
| Apartment | Yes, when available | Not applicable | Not applicable | Visible when the property is more than five years old |
| Villa | Yes, when available | Yes | Yes | Visible when the property is more than five years old |
| Townhouse | Yes, when available | Yes | Yes | Visible when the property is more than five years old |
| Land | Not applicable | Not applicable | Yes | Not applicable |
| Office | Not in v2.1 | Not in v2.1 | Not in v2.1 | Not in v2.1 |
| Retail | Not in v2.1 | Not in v2.1 | Not in v2.1 | Not in v2.1 |
| Warehouse | Not in v2.1 | Not in v2.1 | Not in v2.1 | Not in v2.1 |

All new fields are optional. An empty value must preserve the current evaluation behavior.

## Field definitions

### Project / Building Name

The interface will present one searchable `Project / Building Name` field. Suggestions will be derived from the existing DLD `masterProject` and `project` values, filtered by the selected District / Area whenever possible. The field must support `Unknown` and must not accept a typed value as a verified DLD project unless it exists in the suggestion set.

When a project is selected but does not provide enough comparable evidence, the system will fall back to the district-level evidence and show a clear message. The system must not fabricate project-level comparables or block the valuation solely because the optional project field has no match.

A project selection may also improve the map center when a trusted project coordinate is available. It must not override a manually adjusted property marker without an explicit user action.

### BUA

`BUA` means the built-up area of the property, measured in square metres. It is displayed only for Villa and Townhouse. It is not displayed for Apartment or Land in v2.1. The field is not interchangeable with DLD `area` or `procedureArea` until the data mapping has been validated.

### Plot Area

`Plot Area` means the land parcel area associated with the property, measured in square metres. It is displayed for Villa, Townhouse, and Land. BUA and Plot Area appear in one grouped card named `Property Areas`, with separate labels and short definitions so the user can distinguish the built structure from the land parcel.

For Villa and Townhouse, both values may be entered independently. For Land, only Plot Area is shown. Neither value changes the official valuation during the first UI release; their effect is tested in an isolated analysis first.

### Last Renovation Year

`Last Renovation Year` is displayed only when the existing `Year Built` value indicates that the property is more than five years old. It is shown for Apartment, Villa, and Townhouse, and is hidden for Land and the v2.1 non-residential types.

The field accepts a four-digit year that is not earlier than the construction year and is not later than the current year. It remains optional. In the first release it is captured for analysis and result explanation, but it does not directly change the official valuation until an isolated comparison demonstrates a safe, material benefit.

## Data and evaluation rules

The UI may collect the new values and preserve them in the local valuation payload and result trace. The production calculation must continue to use the current logic until the shadow analysis is reviewed. Any future use in comparable selection or a valuation method must define the source mapping, missing-value behavior, eligible property types, and a rollback path.

The analysis must compare baseline behavior with each field separately and with approved combinations. It must report Accuracy, MAE, bias, P90 absolute error, percentage within ±15%, coverage, and the number of records whose comparable level changes. Results must be segmented by property type and by whether the new field was populated.

## Acceptance criteria

The release is ready for review only when the following are true:

1. Existing Unit Type, Floor, and Parking controls behave exactly as before.
2. New fields appear only for the approved property types and conditions.
3. All new fields remain optional and validate invalid values without creating a price.
4. Project suggestions are DLD-derived, district-aware when possible, and support `Unknown`.
5. Project fallback to District is explicit when project evidence is insufficient.
6. BUA and Plot Area are visually grouped and clearly distinguished.
7. Last Renovation Year follows the five-year visibility rule and validates its year range.
8. Empty new fields preserve the baseline result.
9. The official Accuracy artifact, active calibration, and historical results remain unchanged during the experiment.
10. All unit, browser, and isolated-analysis checks pass before any production evaluator change is proposed.
