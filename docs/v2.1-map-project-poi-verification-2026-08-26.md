## Mobile and POI rendering fix

The autocomplete container now establishes a stacking context above Leaflet controls, and the list has an opaque background, shadow, and higher z-index. The POI markers use a higher marker z-index offset.

The frontend now tries three Overpass endpoints sequentially with an 18-second timeout per endpoint. A successful response is processed and every POI remains Haversine-filtered against the active radius before rendering. A temporary service failure is no longer presented as a confirmed zero-facility result.

A local browser test at `Dubai Marina` returned `186` vital facilities within `1000m`; `30` POI markers were rendered on the map (the intentional display cap), with sample marker coordinates returned by Leaflet. The Hadaeq representative point legitimately returned zero matching OSM facilities within 1000m in the direct query.

The first same-origin production test still returned zero because the backend query builder incorrectly generated selectors such as `[\tamenity=school\t]` instead of the valid Overpass form `[\tamenity\t=\tschool\t]`. This was corrected. The handler integration test then returned `82` facilities with coordinates around Dubai Marina, and the frontend continues to apply the active-radius filter before rendering.

The final live browser test after the selector correction returned `39` vital facilities within `1000m` around Dubai Marina and rendered `30` POI markers on the map, respecting the intentional display cap. The project autocomplete list had z-index `3001`, and its geometry remained above the map when open.

## Marker movement synchronization fix

When a marker move did not match a DLD representative point, the previous District is now preserved in the visible and hidden fields with an explicit `map point outside matched DLD radius` note instead of being cleared. When a marker moves, the previous GIS result and POI markers are cleared immediately, any in-flight request is aborted, a new request identity is created, and a new GIS lookup is scheduled. Only the newest request may update the map.

Local browser checks confirmed that the District remains populated after marker movement, the marker coordinates update, the previous GIS result is cleared, the radius context changes to Searching, and a new refresh is scheduled.

The live marker test confirmed that after firing `dragend`, the District field remained `Dubai Marina`, the visible display retained the district with an explicit outside-radius note, and the marker moved to the new coordinates. The GIS request was still loading at the first 12-second observation; the request identity and abort logic prevent an earlier result from overwriting the new marker state.

After the final deployment, a live `dragend` test moved the marker to `(25.0812, 55.1430)`. The District remained `DUBAI MARINA`, the GIS result recorded the moved coordinates, `37` vital facilities were returned within `1000m`, and `30` POI markers were rendered. The request completed with `gisLoading: false`.
