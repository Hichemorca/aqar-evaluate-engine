# v2.1 User Input Observation Layer

**Status:** approved implementation specification for a shadow-only data collection layer.

## Purpose

The platform will retain the v2.1 optional property fields and record them in a separate analytical store so their relationship with future outcomes can be studied. The observation layer must not modify the official evaluator, Accuracy artifact, DLD cleaning, calibration weights, fallback policy, or historical valuation results.

The layer records what the user entered and what the current engines produced at that moment. It does not treat a user input as verified market truth. A later outcome is a separate field with an explicit source and verification status.

## Scope

The layer covers the existing property types and the approved v2.1 fields. Existing `Detailed Unit Type`, `Floor`, and `Parking Count` remain unchanged in the public form and are captured only as context when already present in the valuation payload.

| Field | Captured for | Initial analytical role |
|---|---|---|
| `projectBuilding` | Apartment, Villa, Townhouse | DLD match status, comparable selection analysis, and project residual study |
| `bua` | Villa, Townhouse | BUA/Plot relationship analysis; no official effect |
| `plotArea` | Villa, Townhouse, Land | Area relationship analysis; no official effect |
| `lastRenovationYear` | Apartment, Villa, Townhouse when visible | Renovation-age analysis; no official effect |

The values remain optional. An empty value is stored as `null` or omitted according to the schema rules below. `Unknown` is represented as an explicit status, not as a fabricated number.

## Record schema

Each accepted event is a versioned JSON object with a server-generated identifier. The canonical schema version is `v2.1-observation-1`.

```json
{
  "observationId": "server-generated-opaque-id",
  "schemaVersion": "v2.1-observation-1",
  "createdAt": "2026-08-26T00:00:00.000Z",
  "source": "public-valuation-form",
  "consent": {
    "analytics": true,
    "consentVersion": "v2.1-observation-consent-1"
  },
  "property": {
    "propertyType": "villa",
    "district": "DUBAI HILLS",
    "yearBuilt": 2020,
    "area": 2500,
    "bedrooms": 4,
    "project": {
      "value": "MAPLE",
      "status": "verified-dld",
      "source": "dld-transactions",
      "normalizedKey": "villa||dubai hills||maple"
    },
    "bua": 420,
    "plotArea": 2500,
    "lastRenovationYear": 2024
  },
  "valuation": {
    "baselineValue": 5000000,
    "shadowValue": 5075000,
    "shadowTrace": {
      "projectMultiplier": 1.01,
      "buaPlotMultiplier": 1.0,
      "renovationMultiplier": 1.005,
      "combinedMultiplier": 1.015
    },
    "calibrationConfigId": "cal-1787651025399",
    "evidenceState": "ready"
  },
  "outcome": {
    "status": "not-provided",
    "value": null,
    "currency": "AED",
    "source": null,
    "verified": false
  }
}
```

## Normalization and validation

The server is authoritative for `observationId`, `createdAt`, `schemaVersion`, and consent metadata. Client-supplied values for these fields are ignored. The server accepts only an allowlisted payload and rejects unknown or oversized fields.

Numeric fields must be finite and use the same units displayed in the form. `bua` and `plotArea` are square metres. `lastRenovationYear` must be an integer between `yearBuilt` and the current calendar year. Fields not applicable to the property type are rejected rather than silently reinterpreted. Project text is never considered verified unless it matches a current DLD-derived suggestion and carries the corresponding normalized key.

The observation endpoint must reject requests without explicit analytics consent. Blank optional fields are valid and preserve the baseline behavior. A failed observation write must never fail or block the valuation itself.

## Privacy and security rules

The observation layer stores property and valuation context only. It must not store names, phone numbers, email addresses, free-form comments, exact user identity, admin tokens, authorization headers, or secrets. IP addresses and user-agent strings are not written to the observation object. The endpoint must use a small request-size limit, same-origin checks where available, and server-side validation.

The initial pilot retention proposal is 24 months for observation events, subject to the owner’s final privacy and retention decision. Records must be append-only or versioned. A later outcome correction must be a separate versioned event referencing the original `observationId`; the original observation is not silently overwritten.

## Storage boundary

The observation layer uses a dedicated storage namespace, separate from `aqar-calibration`. It must never write into `data/accuracy-data.json`, `data/dld-transactions.json`, calibration history, or official market artifacts.

For the current Netlify architecture, the first implementation may use a dedicated Netlify Blobs store named `aqar-input-observations`, with one immutable JSON object per event under a partitioned key such as `events/2026/08/{observationId}.json`. This is a pilot event store, not the official Accuracy database. An export/aggregation job can later copy validated, consented, and de-identified records into a structured analytical database without changing the public evaluator.

## API contract

The initial endpoint is `POST /api/valuation-observation`. It returns a generic success response containing the opaque `observationId`, or a validation error that does not reveal internal storage details. It must not return the full stored event to the browser.

The public endpoint has no read operation. Export and analysis endpoints, if added later, must be admin-authenticated and must not expose secrets. Any future outcome endpoint must require an authenticated or controlled workflow and must preserve the original event.

## Analytical status values

| Status | Meaning |
|---|---|
| `not-provided` | No outcome was supplied with the observation |
| `self-reported` | A user supplied an outcome without independent verification |
| `source-attached` | An outcome includes a declared source but has not been reviewed |
| `verified` | The outcome passed the project’s evidence review and may enter shadow validation |

Only `verified` outcomes may be used in a governed Accuracy experiment. User-input-only records can measure coverage, distributions, missingness, and scenario sensitivity, but cannot prove that a multiplier improves market accuracy.

## Acceptance criteria

1. An empty optional field produces the same official valuation as before and may still produce an observation with `null` optional values when consent is granted.
2. A valid consented observation is stored in the dedicated namespace with a server-generated ID.
3. A request with invalid type-specific fields, invalid renovation year, non-finite numbers, unknown project verification, missing consent, or excessive payload is rejected without affecting valuation.
4. No admin token, identity field, raw authorization header, or secret is stored.
5. The observation write is non-blocking from the user’s valuation perspective.
6. Official Accuracy, calibration, weights, fallback, DLD raw files, and historical results remain byte-for-byte unchanged by observation writes.
7. The schema version and calibration configuration ID make each observation reproducible.
8. Export and analysis are disabled for production activation until the owner reviews the privacy and retention behavior.
